## Findings from the live run (each one changed code)

1. **`state ready` does not clear a config-`disabled` line.** With `disabled` in `haproxy.cfg`, `set server be_app/iwarm_act state ready` was accepted but the line stayed in maint (state file admin_state 5 = config-maint 0x04 + forced-maint 0x01 after our `state maint`); the adapter reported `effect_unverified`. Fix: `disabled` removed from all 14 unbound lines; the `lb` role puts every unbound line (addr `0.0.0.0`) into `state maint` after the stack starts and after a reload (idempotent), and the server-state file carries it. Re-test: `iwarm_act` ready then maint round trip passes; the line ends in its initial state (admin_state 1). Dump + `USR2` reload keeps the lines in maint (admin_state 1 before and after).
2. **The live ops database lacked migration 0015** (`ops.record_haproxy_command` -> `UndefinedFunction`, adapter surfaced `audit_failed`). Migrations 0014 and 0015 were requested to be applied: the migration run applied only `ops/0015_haproxy_routing.sql`; a second run printed "No pending migrations." Discrepancy with the earlier notes: DB-1 recorded ops 0001-0013 at first migrate and DEPLOY-PRIMARY recorded 0014 as applied separately; the live database already had 0014 (15 ops rows, newest `0015_haproxy_routing.sql` now), so the only gap was 0015.
3. **Live check could orphan queued operations** when the lease was briefly held by the reconcile timer (queued -> failed is an invalid transition). The script now retries the lease for 30 s and ends a never-started operation as a terminal no-op. Two orphans from my runs (`769a012c-...`, `1c7c7ecc-...`) were ended as `succeeded` with `noop_reason: orphaned_live_check`.
